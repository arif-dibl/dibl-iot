1. Introduction & Overview

The DIBL IoT Android App is a native Android application that mirrors the functionality of the DIBL IoT Custom UI web application. It communicates with an already-running VPS server via REST API calls to provide IoT device management, monitoring, and control capabilities on mobile devices.

Key Design Principles:
• Native Android Experience — Built with Kotlin + Jetpack Compose for modern, fluid UI
• API Compatibility — Uses the exact same API endpoints as the web Custom UI
• Cookie-based Auth — Shares session with the server via OkHttp CookieJar
• Real-time Polling — 3-second polling for dashboard and asset detail (same as web app)
• Design Fidelity — Matches the web UI's green (#00af50) theme, card layouts, and interaction patterns

1.1 Core Capabilities

  • Authentication: Login and signup through Keycloak-backed authentication
  • Dashboard: Overview with stat cards (total/online/offline devices, rules count), switches, sensors, timer cards, and rule cards
  • Device Management: List, link, rename, and unlink IoT devices; view device details with all attributes
  • Control: Toggle relays/valves, configure timers, manage automation rules
  • Monitoring: View environmental sensor data (temperature, humidity, moisture, NPK) with historical data in table/chart/json modes
  • Provisioning: 4-step wizard for setting up new devices via BLE or manual ID entry
  • User Management: Profile editing, password change, view linked asset partners

2.2 Data Flow Pattern

The app uses a unidirectional data flow:

  1. User Action → UI Composable triggers ViewModel function
  2. ViewModel → Calls Repository method in viewModelScope coroutine
  3. Repository → Calls ApiService Retrofit method, wraps result in Result<T>
  4. ViewModel → Updates MutableStateFlow<UiState> with Success/Failure
  5. UI → Collects StateFlow, recomposes with new state
Polling Pattern: Dashboard and Asset Detail screens use 3-second polling intervals (same as the web Custom UI). The ViewModel launches a coroutine that loops with delay(3000), fetching updated data on each iteration. The polling is started in LaunchedEffect and cancelled in DisposableEffect.

4.2 Networking Configuration

Cookie-based Session Management:
• OkHttpClient uses a thread-safe CookieJar backed by a ConcurrentHashMap
• Login: POST to {prefix}/login with form data → server returns 303 redirect + Set-Cookie
• Subsequent API calls: cookies auto-attached by OkHttp
• followRedirects(false) is set so the app can detect login success (303) vs failure (200 with HTML)

4.3 Error Handling Pattern

All repository methods follow the same pattern:

suspend fun getAssets(prefix: String, username: String): Result<List<Asset>> {
    return try {
        val response = api.getAssets(prefix, username)
        if (response.isSuccessful && response.body() != null) {
            Result.success(response.body()!!.assets ?: emptyList())
        } else {
            Result.failure(Exception("Failed: ${response.code()}"))
        }
    } catch (e: Exception) {
        Result.failure(Exception("Network error: ${e.message}"))
    }
}

5. Authentication Flow

5.1 Login Process

  1. User enters username + password → taps "Sign In"
  2. LoginViewModel.login() calls AuthRepository.login()
  3. Repository POSTs to {prefix}/login with form-encoded username + password
  4. Success: Server responds with HTTP 303 redirect + Set-Cookie header. OkHttp stores the cookie. Repository returns Result.success(username).
  5. Failure: Server responds with HTTP 200 + HTML page containing error message. Repository parses error from HTML patterns (alert-error class, "Invalid" keywords). Returns Result.failure.
  6. On success, credentials (username, baseUrl, prefix) are persisted in DataStore Preferences for session restoration.
  7. ViewModel collects the success state → LaunchedEffect triggers navigation to Dashboard.

5.2 Cookie Persistence

Cookies are stored in memory via OkHttp's CookieJar (ConcurrentHashMap). On app restart, the user needs to re-authenticate. The saved DataStore credentials can be used to restore the session by calling the login endpoint again with saved credentials.

5.3 Logout

AuthRepository.logout() calls NetworkClient.clearCookies() to clear all stored cookies. The LoginViewModel state resets, and navigation returns to the Login screen.

8.2 Navigation Architecture

  • Single Activity: MainActivity hosts NavHost via setContent
  • Start Destination: Determined by authentication state (Login or Dashboard)
  • Bottom Navigation: 5 tabs (Dashboard, Devices, Rules, Timers, More) — visible on main screens

10. Setup & Build Instructions

10.1 Prerequisites

  • Android Studio Hedgehog (2023.1.1) or later
  • JDK 17 (included with Android Studio)
  • Android SDK API 34 (compile target)
  • Gradle (wrapped via gradle-wrapper.properties)

10.2 Build Steps

  1. Open project in Android Studio: File → Open → select ~/Desktop/DIBL-IOT-APP/
  2. Sync Gradle: Android Studio will detect the build.gradle.kts files and prompt to sync. Click "Sync Now".
  3. Configure VPS URL:
    • Option A: On first run, tap the "Server Configuration" expandable section on the login screen and enter your VPS URL (e.g., https://iot.dibl.tech/) and prefix (/customui or empty)
    • Option B: Edit app/build.gradle.kts line 15: change DEFAULT_BASE_URL and DEFAULT_PREFIX buildConfigField values
  4. Build: Run menu → Run 'app' (or Shift+F10). The app will be installed on your connected device or emulator.

10.3 VPS Server Requirements

The VPS must be running the DIBL IoT Custom UI server (FastAPI on port 5000). The Android app connects to the same server endpoints. No server-side changes are needed — the app uses the exact same login, API, and session management endpoints as the existing web Custom UI.

10.4 Network Configuration

  • If connecting to a local dev server over HTTP, set android:usesCleartextTraffic="true" in AndroidManifest.xml (line 23)
  • If using a self-signed certificate, add network security config in res/xml/network_security_config.xml
  • For production (HTTPS with valid certificate), no changes needed

11. Known Issues & Remediation Path

The following issues were identified during a full code review comparing the DIBL IoT Custom UI web application (FastAPI + Jinja2) with the Android app (Jetpack Compose):

🔴 Issue 1 — History Logs Data Never Loads (Critical)

File: HistoryViewModel.kt, lines 75-91

Description: The fetchData() method creates a ProxyRequest object but never calls ApiService.proxyRequest() or any API method. It simply sets fetchLoading = false and returns — no data fetching occurs. Lines 87-88 create a dummy asset fetch call and immediately set loading to false.

Impact: The History Logs page renders its UI but never loads any data from the server. Users see an empty state regardless of actual data availability.

Remediation: Wire fetchData() to call ApiService.proxyRequest() (via AssetRepository or directly) with the correct datapoint API path (/api/{prefix}/asset/datapoint/{assetId}/{attribute}) as a POST request.

🟡 Issue 2 — Timer Start/End Time and Days Not Editable

File: TimersScreen.kt

Description: The TimerTimeField component (lines 144-148) is display-only — it renders text in a Surface with no TimePicker dialog or editable field. Additionally, DaySelector day toggles (lines 163-165) update local state but the changes are never sent to the ViewModel's onSave callback. Only the Status toggle (lines 135-139) actually triggers an API call.

Impact: Users cannot modify timer start/end times or schedule days. The Timers page is effectively read-only.

Remediation: Add a Material3 TimePicker dialog triggered on TimerTimeField click. Wire DaySelector changes through onSave. Persist full timer value map to the API.

🟡 Issue 3 — Chart View is a Placeholder

File: HistoryLogsScreen.kt, lines 176-182

Description: The Chart view mode displays only: "Chart view (requires Chart.js or MPAndroidChart)" — no actual chart is rendered.

Impact: Users cannot visualize data trends. Only Table and JSON views are functional.

Remediation: Integrate a Compose-compatible charting library such as com.patrykandpatrick.vico:compose, io.github.bytebeats:compose-charts, or wrap MPAndroidChart in an AndroidView composable.

⚪ Other Observations

  • Setup Device BLE Scanning: Currently a placeholder — real BLE scanning via Android BLE API is not implemented. Manual Device ID entry works. User has confirmed placeholder is sufficient.
  • QR Scanner: Not integrated in the asset linking flow (web app uses html5-qrcode). Would require CameraX or ML Kit.
  • Offline Mode: No offline caching — all data is fetched from the server.
  • SignupViewModel Scoping: SignupViewModel (line 56) creates a manual CoroutineScope instead of using the built-in viewModelScope — should be refactored for consistency.
