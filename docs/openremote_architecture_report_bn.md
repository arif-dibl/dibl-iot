# সহজ ভাষায় আর্কিটেকচার রিপোর্ট

কেন `docker-compose.yml` ফাইলে সার্টিফিকেট রাখা হয়?
কে কী কাজ করে?

এই রিপোর্টটি **অনলাইন রিসার্চ দ্বারা ভেরিফাইড।**

---
---

## প্রশ্ন ১: কেন `docker-compose.yml`-এ সার্টিফিকেট রাখা হয়?

### উত্তর: Coolify-এর জন্য।

- আপনি সার্ভার চালান **Coolify** দিয়ে।
- Coolify শুধু **একটি `yml` ফাইল** পড়ে পুরো সিস্টেম চালু করে।
- আলাদা করে `.pem` ফাইল সার্ভারে আপলোড করতে হয় না।
- `configs:` ব্লকে লেখা টেক্সট থেকে Coolify **নিজেই ফাইল তৈরি করে** কন্টেইনারের ভেতর দিয়ে দেয়।
- সার্ভার নষ্ট হলে? **শুধু এই একটি ফাইল** দিয়ে আবার সব চালু করা যায়।

> [!NOTE]
> **প্রমাণ:** Coolify-এর ডকুমেন্টেশন অনুযায়ী, `content:` একটি Coolify-এর নিজস্ব ফিচার।
> এটি ডেপ্লয়ের সময় ইনলাইন টেক্সট থেকে ফাইল তৈরি করে কন্টেইনারে ইনজেক্ট করে।
> *(সূত্র: lumadock.com, coolify.io ডকুমেন্টেশন)*

## প্রশ্ন ২: কে কী কাজ করে?

আপনার সিস্টেমে **দুটি অংশ** আছে। দুজনেই আলাদা আলাদা কাজ করে।

---

### 🔒 অংশ ১: প্রক্সি (HAProxy)

এটি হলো সার্ভারের **"মেইন গেট"**।

| কাজ | বিবরণ |
|---|---|
| **Server Certificate ব্যবহার করে** | নিজেকে আসল সার্ভার (`master.senspanel.com`) প্রমাণ করতে |
| **CA Certificate ব্যবহার করে** | ডিভাইসের সার্টিফিকেট চেক করতে (mTLS) |
| **ভুয়া ডিভাইস ব্লক করে** | CA দিয়ে সাইন না করা সার্টিফিকেট থাকলে কানেকশন কেটে দেয় |

> [!IMPORTANT]
> **Server Certificate শুধু প্রক্সিতেই থাকে।**
> Manager-এর এটি দরকার নেই।
> কারণ বাইরের দুনিয়ার সাথে শুধু প্রক্সিই কথা বলে।

---

### 🧠 অংশ ২: ম্যানেজার (OpenRemote Manager)

এটি হলো সার্ভারের **"ব্রেইন"**।

| কাজ | বিবরণ |
|---|---|
| **CA Certificate ব্যবহার করে** | অটো-প্রভিশনিং-এর সময় ডিভাইসের সার্টিফিকেট আবার ভেরিফাই করতে |
| **Asset তৈরি করে** | নতুন ডিভাইসের জন্য স্বয়ংক্রিয়ভাবে Asset এবং Service User তৈরি করে |
| **CN (Common Name) চেক করে** | সার্টিফিকেটের ভেতরের ডিভাইসের নাম (যেমন: db01) বের করে |

> [!WARNING]
> **ম্যানেজারও CA Certificate ব্যবহার করে!**
> এটি প্রক্সির চেয়ে আলাদাভাবে কাজ করে।
> ম্যানেজার তার নিজস্ব Auto Provisioning কনফিগারেশনে রেজিস্টার করা CA দিয়ে সার্টিফিকেট যাচাই করে।
> তবে **Server Certificate** ম্যানেজারে **একেবারেই লাগে না।**

## প্রশ্ন ৩: পুরো প্রক্রিয়াটা কীভাবে কাজ করে?

ধাপে ধাপে:

```
ডিভাইস (db01)
    │
    ▼
┌────────────────────────────────┐
│  ১. প্রক্সি (HAProxy)          │
│     - TLS হ্যান্ডশেক করে       │
│     - Server Cert দেখায়        │
│     - CA দিয়ে ডিভাইস চেক করে  │
│     - ভুয়া হলে? ❌ ব্লক!       │
│     - আসল হলে? ✅ পাস!         │
└────────────────┬───────────────┘
                 │
                 ▼
┌────────────────────────────────┐
│  ২. ম্যানেজার (OpenRemote)     │
│     - ডিভাইসের সার্টিফিকেট    │
│       MQTT পেলোডে পায়          │
│     - নিজের CA দিয়ে আবার      │
│       ভেরিফাই করে              │
│     - CN থেকে নাম বের করে     │
│       (যেমন: "db01")           │
│     - Asset তৈরি করে ✅        │
│     - Service User তৈরি করে ✅ │
└────────────────────────────────┘
```

## সারসংক্ষেপ

| সার্টিফিকেট | প্রক্সি (HAProxy) | ম্যানেজার (Manager) |
|---|---|---|
| **Server Certificate** | ✅ ব্যবহার করে | ❌ লাগে না |
| **CA Certificate** | ✅ mTLS চেকের জন্য | ✅ অটো-প্রভিশনিং ভেরিফিকেশনের জন্য |

> [!NOTE]
> **মূল পার্থক্য:**
> - প্রক্সি → **ট্রান্সপোর্ট লেভেলে** (TLS হ্যান্ডশেকের সময়) সার্টিফিকেট চেক করে।
> - ম্যানেজার → **অ্যাপ্লিকেশন লেভেলে** (MQTT পেলোডের ভেতর পাঠানো সার্টিফিকেট) চেক করে।
> - দুজনেই CA Certificate ব্যবহার করে, কিন্তু **ভিন্ন ভিন্ন উদ্দেশ্যে।**
